# Plugin Registry Documentation

This repository follows the design of the [DSH plugin index](https://deepseek-harness.github.io/deepseek-harness/guide/plugin-market). It provides the plugin information and installation service for the plugins recommended in [awesome-mooling-dsh-plugins](README.md) through a custom plugin index hosted on CloudFlare Workers.

All code and design conventions in this repository may be used as a reference for writing your own project.

To subscribe to the plugin source of [awesome-mooling-dsh-plugins](README.md), add this index subscription link under Plugins: Discover in DSH.

```plaintext
https://mynpm.staringplanet.top/dsh-plugins/index.json
```

Once that is done, the list of recommended plugins appears in your DSH. You can still install plugins outside this repository's index through other index sources or the add-plugin entry.

The rest of this document describes the plugin metadata format this repository requires, and the parsing rules behind it.

## Plugin metadata format

Each plugin should have exactly one metadata file, located under the directory `plugins/by-name/dsh-xx/dsh-xxfullname` or `plugins/by-name/xx/xxfullname`. The number of plugins collected is small for now, but this keeps the index easy to extend to a large number of plugins later.

The metadata file must be named `plugin.yml` and written in the following format:

```yaml
id: dsh-my-plugin
package: dsh-my-plugin
source: npm  # currently github|npm only
repo: https://github.com/MyUserName/dsh-my-plugin
readme:
  zh_CN: README.zh.md  # a relative path or a full link
  en_US: README.md  # a relative path or a full link
  # other language fields are not supported yet; PRs welcome, and maintainers may extend this in the future
dispatch-type: npmjs  # currently npmjs|source|tarball
```

This information is used to generate the temporary plugin list `plugins.txt`, which the CloudFlare Workers service then uses to build and cache the [index data](https://mynpm.staringplanet.top/dsh-plugins/index.json). It is also used to generate the [README](README.zh.md) and its translations.

## Index build

The index is not written by hand. It is generated by CI from the plugin metadata plus the plugin release information read live from the production registry, and then published to a CloudFlare Workers KV store. The whole flow is driven by `.github/workflows/registry.yml`, as two jobs with a real ordering dependency between them.

### Why there is a Workers instance

In the DSH plugin index format, a version has only two possible sources: an npm package, or one commit of a git repository. There is no source type for "just point at this tarball link".

A plugin distributed as a GitHub release tarball, however, usually has not published its package to npm. So that such plugins can still be listed in the index and installed in one step, this repository runs its own CloudFlare Workers as a read-only npm registry:

- it turns GitHub release assets into proper npm packages, so pnpm can recognise and install them normally
- it proxies a hosted package's dependencies to `registry.npmjs.org`, and refuses every other package
- the index itself is served by the same worker, so a client only ever talks to one domain

The second point is not optional. The `peerDependencies` of a converted package are still ordinary npm packages, so a worker that answered only for the packages it hosts could not complete dependency resolution during an install.

That proxying is scoped, though: only packages reachable from a hosted one are allowed, meaning its direct dependencies and their dependencies in turn. Proxying any name on request would turn this domain into a free public npm mirror, where anyone could install any package at this project's expense. The decision lives in `src/allow.ts` and is cached per package in KV: a grant is permanent, while a refusal expires after a day, so a plugin that gains a new dependency later is not blocked by a stale record.

### How data flows

Each CI run does the following.

1. Build the registry data. Read the GitHub release assets of every `dispatch-type: tarball` plugin, compute integrity from the exact tarball bytes, and generate the matching packuments and tarball redirect table.
2. Write the packuments to KV in bulk first, then deploy the worker. The order cannot be reversed: otherwise, at the instant the deploy switches over, a client resolving a hosted package receives a 404 and records it in its own lockfile.
3. After the deploy, `build-index.sh` sparse-clones the DSH source repository at the matching version and produces `dists/index.json` with the index generator from it. Every npm-form entry points at this repository's own registry address.
4. The index is written to the `__index__` KV key. The worker re-reads that key on every request, so publishing a new index needs no redeploy.

Throughout all of this, `dists/` never enters version control: it is a build product, and KV is the single source of truth. That also avoids the noise commits of "update the generated file" on every change.

### Why not distribute through npmjs

Publishing the converted packages to npmjs would let a third party take over a package of the same name, and could not guarantee that the package we produce matches the version our index describes. Running our own registry keeps the source, version and integrity of every package under this repository's CI, with no way for a third party to interfere.

The metadata layer is tightened the same way: `source: npm` may only be combined with `dispatch-type: npmjs`, and pointing at any other third-party npm mirror is rejected outright.

### Local verification

Steps that need credentials can only be run by the maintainer. Everything else can be reproduced locally:

```plaintext
pnpm registry        # generate the packuments and KV bulk file under dists/registry/
pnpm sources         # regenerate dists/plugins.txt from the plugin metadata
pnpm check           # type check
pnpm test            # run the tests
```

## README build

The repository's README contains the complete recommended plugin list, so it has to be generated from a template. The template files live under `templates`.

Because most plugins' names (ids) already convey enough about their purpose, extra information such as a plugin's introduction is left out to save space. Instead, appropriate badges are added automatically below each plugin name, based on the plugin metadata:

- version|tag(commit short hash)
- CI|passing or not
- license|MIT or other (detected automatically through the GitHub API; hidden when unavailable)
- supported DSH version|^0.2.2-rc.1 or other
- any other badge explicitly added in the plugin's own README, without duplicates

As for the version badge, if the plugin is collected through the GitHub release tarball dispatch method, it is shown as Release|version, with the version read from the plugin package information in the corresponding commit, which reduces the chance of a mistake. If there is a pre-release newer than the latest release, it is shown as Pre-release|version.

The plugin name part is a plugin name linked to its source repository, and depending on the language of the README it appears in, a Chinese translation link is added or omitted.

## Local README files

`README.md` and `README.zh.md` are generated and committed by CI, so locally they are an output rather than an input. The repository's git hooks flag both files with `skip-worktree` so local edits stay out of `git status`, which keeps them from being committed by accident or from blocking a pull.

The scripts live under `.githooks`:

- `.githooks/generated-readme on`: hide local edits (the hooks do this after a checkout or a pull)
- `.githooks/generated-readme off`: show them again, so they can be edited and committed
- `.githooks/generated-readme reset`: discard local edits and match the committed copy
- `.githooks/generated-readme status`: report the current state

To edit a README by hand, run `off` first, make the change, commit and push, then run `on`. The `off` state persists, so checkouts and pulls in the meantime will not turn the hiding back on.

`skip-worktree` has one limitation worth knowing: a flagged file cannot be staged at all, not even with `git add -f`, because the flag lives in the index rather than in an ignore rule. Editing one without running `off` does not lose the change, but the hook warns about it and `git status` will not show it.

CI does not need any of this, so the workflow sets `SKIP_README_WORKTREE=1` to keep the hooks out of the way.

## Contributing

PRs to this repository are welcome! Before creating a fork and opening a PR, you need to follow these conventions:

- To submit a plugin you recommend: use `feat: add or update plugin <dsh-plugin-id>`, for example `feat: add or update plugin dsh-my-plugin`, as the commit message and PR title (the PR title is not strictly constrained; the commit message is checked by CI and its body is ignored, and a non-conforming commit will be closed directly unless the PR is a draft). For a PR that passes CI, after 24 hours with no maintainer action, AI review is dispatched to reject or merge it automatically.

> The CI implementation will be pushed to the repository later; until then, everything goes through manual review.

- To change the maintenance conventions or the deployment system in this repository: use [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/), and explain your intent, your changes and your reasoning in the PR body in the language you use. Such changes are reviewed by the maintainer personally, who decides whether to accept them.

If you cannot agree with or follow the conventions above, please do not open a PR!
